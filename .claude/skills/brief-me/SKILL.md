# Context brief intake

The user has pasted a brief that already contains settled decisions. Treat it as the current state of the project, not as a topic to re-explore.

## Steps

1. **Read for structure, not content.** Identify three sets: decisions already taken, open issues, and explicit do-not-revisit items.
2. **Do not reopen settled decisions.** A decision marked as taken is reopened only when new information in the current message contradicts it. Name that information before reopening.
3. **Open the reply at the open issues.** No summary of the brief, no restatement of what it says. The user wrote it; they know what is in it.
4. **Rank the open issues by what unblocks the most.** State which one to solve first and why it blocks the others.
5. **Flag contradictions and gaps once, briefly.** A deadline that does not fit the scope, an open issue whose answer is implied elsewhere, a decision that conflicts with another.
## Checking answers to open issues

When the user answers an open issue, test the answer before accepting it:

- Is it specific enough to act on, or is it a category? ("developer" is a population, not a target user.)
- Does it close the issue, or only rename it?
- Does it force a change to a decision already taken?
  If the answer fails, say so and lay out the distinct options with their consequences. Do not accept a vague answer to keep momentum.

## Output

Scannable: headings, short sections, tables for comparisons. No preamble, no praise for the brief.
